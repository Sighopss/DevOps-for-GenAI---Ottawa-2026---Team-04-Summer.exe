## Trust boundaries

Three boundaries. The first is the one the whole design turns on.

**1. Ingest key ≠ user JWT.** Writes authenticate with an opaque per-tenant `X-Tenant-Key` held in Secrets Manager; reads authenticate with a Cognito **ID** token carrying `custom:tenant_id`. `POST /v1/traces` is configured `authorization_type = "NONE"` — there is no Cognito on the write path — and no `Authorization` header is read there. A leaked ingest key can append spans for one tenant; it cannot read anything.

**2. Tenant isolation is enforced at read, not at the gateway.** The JWT authorizer proves only that a token is genuine and from our pool. The comparison of the token's `custom:tenant_id` against the stored tenant, and the resulting **403 rather than 404**, is application logic inside `vault-read`. Stating this precisely matters: a reviewer who assumes API Gateway enforces it would be looking in the wrong place, and an access token (which carries no `custom:tenant_id`) passes the authorizer but must fail closed with `401` in the handler.

**3. The recorder is untrusted by the vault.** `sdk/tracevault` computes a masked `prompt_preview` before anything leaves the process, but that value is a *hint*. `vault-ingest` re-runs redaction over every free-text field it receives, so a buggy or hostile recorder cannot push raw PII past the vault. Redaction is authoritative at ingest, not at emit.

## Red-team evidence

The handbook asks teams to *show one attack*. Two are contracted as the demo attacks:

1. **Synthetic email + SSN in a prompt → zero raw PII at rest.** Covered now by `vault/tests/ingest/test_pipeline.py::test_pii_in_any_text_field_never_reaches_rest` and the adversarial suite. Demonstrable against a running system once deployed.
2. **tenant-b presenting a tenant-a `trace_id` → 403.** **Not demonstrable yet** — the read handler does not exist (#15).

Attacks against the deployed system, and the fixes they produce, are issue #54 and require an apply first.

## Honest summary of coverage

Both properties this product exists for are **asymmetrically covered**: redaction is implemented and heavily tested (83 vault tests, including an adversarial suite), while tenant isolation is contracted, frozen in the error envelope, and **not yet implemented**. Nothing in this repository has been penetration-tested against a live endpoint, because nothing is deployed.

Cloud controls in the table above marked *reviewed-not-verified* are exactly that: the Terraform asserts them and `validate` passes, but no `terraform apply` has run. Treat them as design intent with a reviewable source, not as running controls.
