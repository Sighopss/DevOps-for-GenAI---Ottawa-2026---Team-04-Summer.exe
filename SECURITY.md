## Trust boundaries

Three boundaries. The first is the one the whole design turns on.

**1. Ingest key ≠ user JWT.** Writes authenticate with an opaque per-tenant `X-Tenant-Key` held in Secrets Manager; reads authenticate with a Cognito **ID** token carrying `custom:tenant_id`. `POST /v1/traces` is configured `authorization_type = "NONE"` — there is no Cognito on the write path — and no `Authorization` header is read there. A leaked ingest key can append spans for one tenant; it cannot read anything.

**2. Tenant isolation is enforced at read, not at the gateway.** The JWT authorizer proves only that a token is genuine and from our pool. The comparison of the token's `custom:tenant_id` against the stored tenant, and the resulting **403 rather than 404**, is application logic inside `vault-read`. Stating this precisely matters: a reviewer who assumes API Gateway enforces it would be looking in the wrong place, and an access token (which carries no `custom:tenant_id`) passes the authorizer but must fail closed with `401` in the handler.

**3. The recorder is untrusted by the vault.** `sdk/tracevault` computes a masked `prompt_preview` before anything leaves the process, but that value is a *hint*. `vault-ingest` re-runs redaction over every free-text field it receives, so a buggy or hostile recorder cannot push raw PII past the vault. Redaction is authoritative at ingest, not at emit.

## Red-team evidence

The handbook asks teams to *show one attack*. Two are contracted as the demo attacks:

1. **Synthetic email + SSN in a prompt → zero raw PII at rest.** Covered by `vault/tests/ingest/test_pipeline.py::test_pii_in_any_text_field_never_reaches_rest` and the adversarial suite, and **demonstrated live 2026-08-22**: a flight with a real email/SSN/AWS-key/nested-email ingested through the deployed pipeline, then the raw S3 object and DynamoDB item read directly with the `tracevault-alexis` role — 0 raw-PII hits, both stores masked and KMS-encrypted (`docs/RED_TEAM.md` B2/B2-rest).
2. **tenant-b presenting a tenant-a `trace_id` → 403.** Implemented and tested (`vault/read/tenant_guard.py`, `vault/tests/read/test_isolation.py`) and **demonstrated live** — tenant-b's Cognito ID token against the tenant-a trace returned `403 "tenant mismatch"` with no spans (`docs/RED_TEAM.md` B1).

Attacks against the deployed system and the fixes they produced are in `docs/RED_TEAM.md` (issue #54): the full red-team harness runs `14/14` live. Of the two false infra claims it surfaced, the WAF one is now fixed and verified (#100); the TLS floor remains open (#101).

## Honest summary of coverage

Both properties this product exists for are **implemented, tested, deployed, and demonstrated in operation** as of 2026-08-22: 109 vault tests (including an adversarial redaction suite and cross-tenant isolation tests), and a live red-team run that proved zero raw PII at rest (reading S3 + DynamoDB directly), cross-tenant 403, audited access, and clean logs (`docs/RED_TEAM.md`).

The remaining honesty caveats are infrastructure, not vault behaviour: the **edge TLS floor is TLSv1** (default CloudFront cert, #101), and while **WAF now guards the edge and is demonstrably blocking** (#100, see the Perimeter row), it cannot front an HTTP API — so ingest flood bounds still rest on the in-Lambda caps + API Gateway throttling, not WAF.

Cloud controls in the table above marked *reviewed-not-tested* are exactly that: the Terraform asserts them and the stack was applied 2026-08-22, but no automated assertion re-checks them as the stack changes. Treat them as reviewable, applied controls without a regression test, not as running-and-verified ones.
